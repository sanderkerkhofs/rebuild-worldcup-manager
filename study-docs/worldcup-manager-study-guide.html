1. Project in 60 Seconds

Worldcup Manager is a full-stack tournament management app. It allows users to view competition data, and allows role-based users (admin/referee) to manage match progress, results, goals, and tournament progression.

  • Frontend: Next.js + React + TypeScript for pages and UI.
  • Backend: Express + TypeScript for API endpoints and business logic.
  • Database: PostgreSQL with Prisma ORM.
  • Security: JWT authentication + role-based authorization.
  • Documentation/testing: Swagger + Jest tests + manual API checks.

3. Node, Express, Next Explained Simply

What is Node.js?

Node.js is the runtime that executes JavaScript outside the browser. In this project, Node runs your backend server and tool scripts.

Why Express?

Express gives you a clean structure for APIs: route handlers, middleware, and error handling. Your backend uses thin controllers and puts business rules in services.

Why Next.js?

Next.js gives file-based routing, easy page composition, and a production-ready React setup. For a student project, it reduces setup complexity compared to building React router/config from zero.

You use the Pages Router, which is straightforward for learning and matches your route-per-file page structure.

4. Architecture and Request Process Flow

Monorepo structure

root
|- back-end   (Express API, Prisma)
|- front-end  (Next.js UI)
|- genAI-docs (project documentation)
|- study-docs (exam study material)

Standard request flow

Browser page action
-> front-end service function
-> shared apiRequest() wrapper (adds JWT if present)
-> Express route controller
-> middleware (auth + role checks if protected)
-> service layer business logic
-> Prisma query/mutation
-> PostgreSQL
-> response JSON
-> SWR revalidation and UI rerender

Important separation of concerns

  • Controllers: map HTTP to service functions.
  • Services: enforce business rules (round lock, role assignment, score validity).
  • Models: pure domain validations (example: no draw in knockout).
  • Prisma client: data persistence and relation loading.

5. Domain Entities and Relationships

Main entities

  • User: admin, referee, or normal user.
  • Team: nation/team metadata.
  • Player: belongs to a team, has position and availability status.
  • Match: two teams, optional referee, scores, round, and status.
  • Goal: links match + player + team (goal events).

Key constraints you can mention in exam

  • User username is unique.
  • Player has unique shirt number per team (teamId + shirtNumber).
  • Goal links to existing match/player/team with cascade deletion.
  • Match progression uses roundOrderNumber 1 to 4.

Business meaning of enums

  • UserRole: ADMIN, REFEREE, USER.
  • PlayerStatus: AVAILABLE, UNAVAILABLE.
  • MatchStatus: PLANNED, NOT_STARTED, IN_PROGRESS, FINISHED.

6. Backend Deep Dive

Backend startup and middleware

  • Global middleware: helmet, cors, JSON parser.
  • Routers mounted at /api/auth, /api/competition, /api/matches, /api/players, /api/users.
  • Error handler standardizes error responses.

Auth flow on backend

  1. Register/login in authService.
  2. Password hashing/verification with bcrypt.
  3. JWT signed with user id as subject and role/team metadata.
  4. authenticateToken middleware verifies token and sets req.authUser.
  5. requireRoles middleware blocks forbidden roles.

Core business rules worth defending

  • Referee can edit only assigned matches (except admin who can edit all).
  • Knockout matches cannot end in draw (validateNonDraw).
  • Round N cannot be edited until round N-1 is complete.
  • When all matches in a round are finished, winners auto-progress to next round.
  • Goal creation checks player availability and team correctness.

Tournament operations

  • simulateRound(round): admin-only random scoring with draw prevention + goal sync.
  • resetMatches(): admin-only reset of goals and round statuses.
  • getOverview(): aggregated competition snapshot for frontend dashboard.

Testing scope implemented

  • Model tests: validate score and shirt number invariants.
  • Service tests: role guard checks for simulate/reset operations.

7. Frontend Deep Dive

Global composition

In _app.tsx, every page is wrapped with I18nProvider, SessionProvider, and Layout. This centralizes language state, auth session state, and consistent navigation/UI shell.

Role-based pages

  • Public: home, login, register.
  • Authenticated: matches and stats pages.
  • Admin only: admin page (simulate/reset/list users).
  • Referee only: referee page (assigned matches).

API consumption pattern

  1. Page calls service function.
  2. Service uses shared apiRequest wrapper.
  3. apiRequest adds Authorization bearer token when available.
  4. SWR caches and revalidates after mutations.

Useful frontend interview notes

  • You avoided direct fetch calls inside pages by using service modules.
  • You used conditional SWR keys to avoid unauthorized fetches.
  • You handled loading, error, and empty states in pages.
  • You implemented lightweight i18n with persisted locale.

8. Authentication, Authorization, and Security

Authentication

  • Login/register returns token + safe user object.
  • Token and user are saved in localStorage.
  • SessionProvider restores session after app mounts.

Authorization

  • Frontend: hides/displays pages based on role for UX clarity.
  • Backend: final authority via requireRoles and assignment checks.

Security controls present

  • Password hashing with bcrypt.
  • JWT secret from environment variable.
  • Helmet for secure HTTP headers.
  • CORS allow list with env configuration.
  • Centralized error messages (no stack leaks to client).
Potential config trap to know for defense: frontend default API base URL falls back to http://localhost:3001/api, while backend usually runs on http://localhost:3000/api. In practice, set NEXT_PUBLIC_API_BASE_URL correctly in frontend env to avoid mismatch.

9. Swagger and API Testing Strategy

Swagger is available at /api-docs and is generated from backend route annotations plus shared schema definitions. Use it to prove endpoint behavior quickly in demos.

How to demonstrate in exam

  1. Open /status to show service health.
  2. Login in Swagger to get a JWT token.
  3. Use Authorize button with Bearer token.
  4. Test role-protected endpoint (for example simulate round) as admin.
  5. Test forbidden case with user/referee token.

What examiners like to hear

  • Swagger helps contract validation and manual regression checks.
  • It speeds up backend debugging before touching frontend.
  • It communicates API behavior clearly to teammates.

11. Exam Interview Questions with Model Answers

Q1. Why did you choose Next.js instead of plain React?

Next.js gives me a clear file-based routing structure and production-ready tooling with less setup. For this project, that let me focus on business logic and role-based flows instead of custom build/router config.

Q2. Why Prisma instead of raw SQL?

Prisma gave me typed queries, safer refactors, and easier relation loading. I still use PostgreSQL under the hood, but Prisma improves developer speed and readability for a student-level full-stack project.

Q3. Where is business logic located and why?

In services, not controllers. Controllers only map HTTP request/response. Services implement rules like round locks, assignment checks, and progression. This keeps code maintainable and testable.

Q4. How do you prevent unauthorized updates?

Backend middleware authenticates JWT and checks roles. For matches, service logic additionally verifies referee assignment. Frontend role checks are only UX guidance; backend enforces security.

Q5. How is knockout progression implemented?

After a match/round is finished, services verify all matches in that round are finished with non-draw scores. Then winners are computed and assigned into next round fixtures in order.

Q6. How do you handle score-goal consistency?

When result is set, goalSyncService regenerates goal events based on score. This keeps total goals aligned with match score.

Q7. Why use SWR?

SWR simplifies fetching/caching/revalidation of server data. After mutations, I call mutate to refresh UI, which avoids manual data synchronization bugs.

Q8. What are the weaknesses in current version?

Limited automated tests, localStorage token storage trade-offs, and some places where stricter validation could be added (for example stronger DTO schemas on all endpoints). I can describe concrete improvements.

Q9. What does Express middleware give you in this project?

Reusable cross-cutting logic: auth verification, role checks, async error forwarding, and centralized error formatting.

Q10. Explain one end-to-end feature flow.

Example update result: user action in match detail page -> frontend service PUT call -> backend auth and role checks -> matchService validates score and round lock -> database update -> goals synchronized -> response -> SWR mutate rerenders page.

12. How to Defend Your Design Choices

  • Say you optimized for clarity and maintainability as a learning project.
  • Explain separation of concerns: controller/service/model/repository responsibilities.
  • Show role-based security is enforced server-side, not only hidden in UI.
  • Point to Swagger as practical contract documentation and test utility.
  • Acknowledge current limitations and propose realistic next steps (shows engineering maturity).

13. Improvement Ideas if Examiner Asks "What Next?"

  1. Add more service-level tests (round progression edge cases, goal update consistency, auth failure scenarios).
  2. Add request schema validation consistently with Zod at controller boundaries.
  3. Move JWT from localStorage to httpOnly cookies for stronger XSS resilience.
  4. Add structured logging and request correlation IDs for debugging.
  5. Add CI workflow running lint, tests, and build automatically.
  6. Improve referee UX by selecting players from dropdowns instead of entering IDs manually.
